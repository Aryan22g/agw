agw runs your agents inside a boundary they cannot opt out of, even with root. It refuses what policy does not allow, and it records everything they did and attempted as evidence anyone can verify with a file and a public key. No account, no network, no trust in us.

Isolation that assumes the agent stays put is not isolation.

The agent “read the EC2 node role credentials from the instance metadata service.” Hugging Face, Anatomy of a Frontier Lab Agent Intrusion, 27 July 2026. The agent came from a cyber-capability evaluation, escaped its sandbox through a zero-day, and later used a harvested signing key to mint its own identity tokens.

Every control that depends on the agent choosing to use it failed the moment the agent stopped cooperating. agw puts enforcement outside the agent's trust domain. It is honest about what that does and does not change.

  1. No effectZero-day in the registry cache proxy; a public eval harness; template injection in a data loader. Someone else's vulnerabilities.
  2. PreventedCredentials from the metadata endpoint. Refused at the proxy and the firewall, whatever the policy says.
  3. ReducedEnvironment secrets. The supervisor's environment no longer crosses into the sandbox.
  4. ReducedOne credential shared across clusters. A confined agent reaches only the destinations its policy names.
  5. TransformedForensics. Every attempt, allowed or refused, in a chain that verifies offline.

Three verbs. Every feature serves one.

Confine

The agent reaches only what policy allows. It cannot opt out, because the enforcement point is outside its trust domain: a network namespace, a sidecar, a firewall rule it cannot remove. Cloud metadata, link-local and NAT64 space are refused no matter what the policy says.

agw run · sidecar-init · proxy
Decide

Every egress and every MCP tool call is checked before it happens, against a default-deny policy, with a stable reason code when refused. The kill switch cuts a running agent off in about a millisecond, and it does not ask the agent first.

agw mcp · agw suspend · agw policy explain
Prove

Every allow and every refusal lands in a hash-chained, signed evidence log, and is recorded before the action. If it cannot be recorded, it does not happen. Anyone can verify the log with a file and a public key.

agw audit verify · agw-verify · RFC-0009

One command: contained, recorded, verifiable

The command runs in its own network namespace. Its only way out is a proxy that enforces policy, backed by a firewall it cannot remove. Nothing from your shell's environment crosses unless you name it. agw suspend from another terminal cuts connections, refuses new ones and kills the process group.

tested · as root on Linux · kill switch asserted in CI 
sudo agw run --policy agw-policy.yaml \
  --env OPENAI_API_KEY -- python agent.py

# from another terminal
sudo agw suspend --workload my-agent --reason "anomalous behaviour"
#   connections closed  2
#   teardown            246µs

A native sidecar, with the cluster enforcing its preconditions

An init step lets only the proxy's UID leave the pod. An admission policy then refuses pods whose other containers keep capabilities, run as the proxy's UID or use the host network. It also refuses a kubectl debug container with NET_ADMIN added later.

tested · Kubernetes 1.33 · root attacker in the pod 
kubectl apply -f integrations/kubernetes/admission-policy.yaml
kubectl apply -f integrations/kubernetes/confined-agent.yaml

# label your own pods, keep the agent's securityContext:
#   metadata.labels:  agw.dev/confined: "true"
#   capabilities:     drop: ["ALL"]

What it does not stop.

We do not prevent agents from going rogue. We bound what a rogue agent can reach, and make everything it attempted provable. Here is where that line falls, with the test behind every “yes”.

Tested like an attacker would test it.

  • An adversarial environment, scored by the worldA generated enterprise with a hostile agent in it. Each service keeps its own receipt of what it received, and that is compared with the evidence agw wrote. Egress with no record is the one failure a product cannot report about itself. 9,450 episodes across 150 generated worlds: none.
  • Root, on real Linux, in CIThe containment tests build real namespaces and firewall rules, then check that an agent with root cannot reach the metadata endpoint or remove the rules. CI fails if they are skipped.
  • Three verifiers, one specificationGo, standard-library Go and JavaScript implementations, written separately and run against each other on thousands of mutated logs. Where they disagreed, the specification was ambiguous or one of them was wrong.
  • Against the real thingThe official MCP client and server, the Python and Node OpenTelemetry SDKs, the OpenTelemetry Collector, a Kubernetes cluster and Docker Compose, each with the configuration published here.

What that testing found in our own code

Published, because the way to trust a security product is to see how its failures were found and fixed. SECURITY.md keeps the list.

  1. A crafted MCP message was authorized as one method and executed as a forbidden tool call.found by a server that parses like Node and Python do
  2. A verified log could display a decision other than the one that was signed.found by differential testing of two verifiers
  3. The policy allowlist could be used to reopen the cloud metadata range.found by the adversarial environment
  4. The sandbox inherited the operator's environment, credentials included.found by running agw run for real
  5. Keeping the signing key in a separate process stopped all traffic at the first checkpoint.found by testing separate custody end to end
  6. Two verifiers wrapped around to 1.8×1019 “unanchored records” on a reordered log.found by the JavaScript verifier on this page

Built for the rooms where this matters most.

Labs and evaluators

Run an agent against a benchmark with shell and network access, contained, and publish the evidence alongside the paper. A reviewer verifies it offline, air-gapped, with no account. You get a containment control and a reproducibility artifact from one command.

sudo agw run --policy eval.yaml -- python harness.py

Platform and security teams

Start with a record of what your production agents actually do. Draft a policy from it, rehearse it, then enforce it one agent at a time. Each step is defensible in a change review on its own. When something goes wrong at 03:00, cut the agent off in about a millisecond and reconstruct from a log nobody could have edited.

agw suspend --workload agent-support-01

Compliance

EU AI Act Article 12 asks for automatic, tamper-evident event logs over a system's lifetime, kept for at least six months. agw records at a point the agent cannot bypass, without storing payloads, and exports bundles a third party can verify. The article-by-article mapping says what it covers and what it does not.

agw audit export evidence.jsonl --from 2026-07-01T00:00:00Z --out q3.json

Evidence you do not have to trust us for.

Verification that only a vendor can perform is not verification. The evidence format is a specification a stranger can implement, with test vectors that check whether they did.

RFC-0009The evidence chain: an exact byte encoding, signed checkpoints, and a normative verification algorithm with stable problem codes.
39 conformance vectorsExpected results written from the specification, including every edge where common JSON and timestamp parsers disagree.
3 implementationsThe reference, agw-verify (one file, standard library, no sockets) and the JavaScript on this page.
